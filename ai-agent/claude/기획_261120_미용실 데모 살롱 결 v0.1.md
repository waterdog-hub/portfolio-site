# 미용실 예약 데모 기획: 살롱 결

**파일 위치**: `ai-agent/claude/기획_261120_미용실 데모 살롱 결 v0.1.md` (포트폴리오 저장소에 둔다. 새 프로젝트 `CLAUDE.md`가 이 경로를 가리킨다)
**작성일**: 2026-11-20
**버전**: v0.1
**설명**: 포트폴리오에 넣을 가상의 미용실 "살롱 결" 예약 데모의 목표, 범위, 화면, 예약 규칙, 결정 기록. 상위 기획서 D-06에 대응한다.

## 1. 목표와 이유

- 포트폴리오에는 회원제 서비스 사례 3건과 보기만 하는 가게 홈페이지(하루밀 베이커리)가 있다. 그런데 "가게 운영을 돕는 기능"까지 보여 주는 가게 사례가 없다.
- 운영자가 받고 싶은 업종 중 미용실은 예약이 핵심이다. 그래서 이 데모는 **손님 예약 화면**과 **사장님 관리 화면**을 함께 보여 준다. 크몽·숨고에서 "홈페이지 + 예약 기능"으로 단가를 올리는 근거가 된다.
- 핵심 장면: 방문자가 손님 화면에서 예약하고 "사장님 화면 보기"를 누르면, **방금 넣은 예약이 사장님 화면에 들어와 있고 확정할 수 있다.**
- 성공 기준: 미용실 사장님이 데모를 둘러보고 "우리 가게에도 이렇게 예약받고 싶다"며 플랫폼으로 문의하는 것.

## 2. 범위

| 구분 | 포함 | 제외 |
|------|------|------|
| 손님 | 가게 소개, 시술·디자이너·날짜·시간 고르기, 예약 신청, 예약 완료 화면 | 회원가입, 손님의 예약 변경·취소, 결제·예약금 |
| 사장님 | 날짜별 예약 목록, 확정·취소, 영업시간·휴무일 설정 | 로그인(데모라서 없음), 시술 메뉴·디자이너 추가·수정, 매출 통계 |
| 알림 | 없음 (화면에 "실서비스에서는 문자·알림톡을 붙일 수 있어요" 안내만) | 문자·카카오 알림톡·이메일 발송 |
| 가게 | 지어낸 가게 "살롱 결" | 실제 가게 |
| 사진 | 무료 사진 사이트의 상업 이용 가능 사진 | AI 이미지, 직접 촬영 |

**안티 목표** (기술적으로 돌아가도 실패로 보는 것)
- 방문자가 남이 넣은 예약·이름을 보는 것 (장난 입력이 그대로 노출됨)
- 방문자의 실제 이름·전화번호가 서버에 쌓이는 것
- 실제 가게나 실제 연락처로 오해받는 것 (D-02)
- 휴대폰에서 예약 단계가 투박하게 깜박이거나, 이미 찬 시간을 고를 수 있는 것
- 하루밀이나 포트폴리오와 같은 디자인처럼 보이는 것

## 3. 체험 방식: 방문자마다 따로 (운영자 결정)

| 안 | 내용 | 결과 |
|----|------|------|
| **① 방문자마다 따로** | 처음 들어오면 그 방문자만 보는 예시 가게 데이터를 만든다. 24시간 뒤 지운다 | **선택** |
| ② 모두가 함께 씀 | 데모 가게 하나를 공개 계정으로 함께 쓰고 매일 밤 초기화 | 남의 예약·장난 입력이 보여 탈락 |

- 방문자 구분은 쿠키로 한다 (무작위 값, 로그인 없음). 쿠키가 없거나 데이터가 지워졌으면 새 예시 가게를 만든다.
- 새 예시 가게에는 디자이너 3명, 시술 메뉴, 미리 채운 예약(오늘·내일·모레에 몇 건, 대기·확정 섞어서)이 들어간다. 날짜는 만들어지는 날 기준으로 계산해 언제 들어와도 "지금" 예약처럼 보이게 한다.
- 24시간이 지난 데이터는 지운다.
- 장난 입력 대비: 한 방문자 데이터의 예약 수에 상한을 둔다 (값은 만드는 사람이 정한다).
- **복제 단위** (Claude 결정): 가게 하나를 통째로 방문자마다 만든다. 디자이너·시술·영업시간·휴무·예약 모두 그 방문자의 가게에 속한다. 그래야 사장님 화면에서 영업 설정을 바꿔도 다른 방문자에게 영향이 없고, 지울 때도 가게 하나만 지우면 된다.
- **두 화면 잇기** (Claude 결정): 손님 화면과 사장님 화면은 같은 쿠키로 같은 가게를 본다. 사장님 화면 주소를 먼저 열어도 쿠키가 없으면 새 예시 가게를 만들어 보여 준다. 쿠키가 막힌 브라우저에서는 매 요청마다 새 가게가 생겨 핵심 장면이 깨지므로, 쿠키가 저장되지 않은 것을 알아채면 "쿠키를 허용해야 체험할 수 있어요" 안내를 띄운다. 주소에 토큰을 싣는 대체 방식은 쓰지 않는다 (주소를 공유하면 남의 데이터가 보이기 때문).

## 4. 화면 구성

모든 화면은 휴대폰 우선. 위쪽에 데모 띠("포트폴리오용 데모입니다 · 손님 화면 / 사장님 화면 전환")를 둔다.

### 손님 화면

| ID | 화면 | 내용 |
|----|------|------|
| C-01 | 가게 소개 | 첫 화면 사진, "당신에게 맞는 선, 살롱 결", [예약하기]. 디자이너 소개, 시술 가격표, 오시는 길(가짜 주소·지도 그림), 바닥글(데모 안내·사진 출처·포트폴리오로 돌아가기) |
| C-02 | 예약 | 한 페이지 안에서 단계 진행: ① 시술 ② 디자이너 ③ 날짜 ④ 시간 ⑤ 이름·전화번호. 이전 단계 선택이 바뀌면 뒤 단계를 다시 계산. 이미 찬 시간·지난 시간·휴무일은 고를 수 없게 표시 |
| C-03 | 예약 완료 | 예약 내용 요약, 상태 "확정 대기", [사장님 화면에서 확인해 보기] 버튼 (핵심 장면으로 안내) |

### 사장님 화면

| ID | 화면 | 내용 |
|----|------|------|
| A-01 | 예약 목록 | 날짜 고르기(오늘 기본, 앞뒤 이동), 그날 예약을 시간순으로. 디자이너별로 구분해 보이게. 대기 건은 눈에 띄게. 방금 넣은 예약은 "새 예약" 표시 |
| A-02 | 예약 처리 | 목록에서 대기 → 확정, 대기·확정 → 취소. 화면 새로 고침 없이 바뀐다 |
| A-03 | 영업 설정 | 요일별 영업시간, 특정 날짜 휴무 지정·해제. 바꾸면 손님 화면의 고를 수 있는 시간에 바로 반영 |

## 5. 예약 규칙

- 시간대: 한국 시간(Asia/Seoul).
- 시간 단위 30분. 시술마다 걸리는 시간이 있고(예: 커트 1시간, 펌·염색 2시간), 그 시간 동안 그 디자이너는 다른 예약을 받을 수 없다.
- 기본 영업: 10:00–20:00, 화요일 정기 휴무. 시술이 마감 시간을 넘기는 시작 시간은 고를 수 없다.
- 예약 가능 기간: 오늘(지난 시간 제외)부터 14일 뒤까지.
- 상태: 손님이 신청하면 **대기** → 사장님이 **확정** 또는 **취소**. 취소된 예약의 시간은 다시 열린다.
- 이미 예약(대기·확정)이 있는 날을 휴무로 바꾸려 하면 막고 안내한다. 영업시간을 줄여 기존 예약이 범위를 벗어나는 경우도 같다.
- 두 사람이 같은 시간을 동시에 신청해도 겹쳐 저장되지 않게 서버에서 한 번 더 확인한다. 겹치면 "방금 다른 예약이 들어온 시간이에요" 안내와 함께 ④ 시간 고르기로 돌아가 최신 빈 시간을 다시 보여 준다. 예약 상한을 넘으면 안내 문구만 띄운다. (Claude 결정)
- "오늘"과 14일 기간은 요청할 때마다 현재 시각으로 다시 계산한다. 예시 예약은 가게가 만들어진 날 기준이라, 자정을 넘기면 일부가 지난 예약이 되는 것은 허용한다 (최대 24시간만 남는 데이터라서). 테스트에서 시각을 고정할 수 있게 현재 시각은 한 함수에서만 얻는다. (Claude 결정)
- 사장님 화면의 "새 예약" 표시는 예시 데이터가 아니라 방문자가 직접 넣은 예약 중 아직 대기인 건에 붙인다. 예약에 "예시 데이터인지" 표시 하나만 있으면 된다. (Claude 결정)
- 이름·전화번호 칸은 "예시 이름"·"000-0000-0000"을 미리 채워 두고 "실제 정보를 넣지 마세요"라고 안내한다. 전화번호는 형식만 가볍게 확인한다.

## 6. 만드는 방법

### 접근 비교 (운영자가 ①을 골랐다)

| 안 | 내용 | 장점 | 단점 |
|----|------|------|------|
| **① smart-voca 구조** | FastAPI가 Jinja2로 페이지를 내려주고, 예약 단계·확정/취소는 바닐라 JS가 JSON API를 부른다 | 검증된 구조, 휴대폰에서 매끄러움, "API도 있다"고 말할 수 있음 | ②보다 JS가 조금 많음 |
| ② 페이지 이동만 | JS 없이 단계마다 폼 전송 | 가장 단순 | 단계마다 화면이 새로 그려져 투박함 |
| ③ 화면 분리 (React 등) | 프론트·백엔드 프로젝트 분리 | 요즘 방식 | 빌드 도구 필요(D-01 정신과 어긋남), 만들고 배울 양 두 배 |

### 정해진 것

- 별도 프로젝트 `C:\Users\PC2602\salon-demo` (로컬 git 저장소, `main` 기본 브랜치). 포트폴리오와 같은 `docs/개발방법론.md` 방식을 따르고 프로젝트 `CLAUDE.md`를 둔다.
- Python FastAPI, SQLAlchemy, Jinja2, unittest (smart-voca와 같은 테스트 방식). 라이브러리 버전은 smart-voca `requirements.txt`를 기준으로 맞춘다. 실행은 `.venv`.
- DB는 SQLite 파일 하나 (데이터가 하루만 남는 데모라 운영 DB가 따로 필요 없다).
- 화면은 순수 HTML·CSS·바닐라 JS, 빌드 도구 없음. 색은 CSS `:root` 변수만, `style=""` 금지, 접근성 기본(포트폴리오 코드 작성 규칙과 같다).
- 분위기는 시안 **B 로즈 베이지**: 분홍빛 베이지 배경, 둥근 버튼, 제목 Noto Serif KR, 본문 Pretendard. 강조색은 시안의 `#b06f60` 계열.
- 연락처·주소는 누가 봐도 가짜(전화 `000-0000-0000`, 주소 "OO시 OO구 OO로 00", 인스타 `href="#"`).
- 사진은 내려받아 줄여 프로젝트 안에 둔다(핫링크 금지). 내려받기 전에 목록과 출처를 운영자에게 보여 주고 허락을 받는다. 출처는 `CREDITS.md`.
- 데스크톱(1280px)과 휴대폰(375px)에서 확인한다.
- 배포 위치는 정하지 않는다. 포트폴리오 배포를 정할 때 함께 정한다. 다만 한 대의 작은 서버에서 SQLite로 돌 수 있게 만든다.
- 포트폴리오 카드 연결은 배포 주소가 생긴 뒤에 한다 (이 문서 범위 밖).
